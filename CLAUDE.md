# krzhv.com.ua — правила для агента

Сайт клінічного психолога Сергія Коржова (КПТ, онлайн, українською). Eleventy, GitHub Pages, публікація = злиття в `main` (GitHub Actions збирає сайт, запускає `npm test`, деплоїть за 1–2 хв). Репозиторій **публічний**.

Автор: власник сайту. Мова текстів: українська, проста, короткі абзаци, без академічного жаргону. Терміни КПТ пояснювати при першій появі. Стиль і структуру брати з наявних матеріалів (`src/statti/`, `src/blog/`).

## Правило публікації (найважливіше)
- Нову статтю чи пост у `main` **не зливати, доки власник не відповів словом «ОК»** (саме так; будь-яка інша відповідь = правки, не публікація).
- Чернетку готувати в гілці `draft/<slug>`. Правки власника вносити в ту саму гілку й надсилати знову.
- Після «ОК»: оновити `reviewed` та `updated` на поточну дату, запустити `npm install && npm test`, злити в `main`, перевірити, що збірка в Actions зелена, а сторінка відкривається.
- Не змінювати шаблони, CSS, квізи (`src/kviz/`), відгуки, `/secret/`, workflows без прямого прохання власника. Кризову логіку квізів не чіпати.
- Не видаляти файли без прохання. Не робити force-push.

## Наукова достовірність (головна вимога)
- Перед текстом: мінімум 2–3 реальні пошуки джерел (механізм, ефективність КПТ, поширеність). Пріоритет: клінічні настанови, систематичні огляди, мета-аналізи, першоджерела. Не цитувати чужі сайти замість першоджерел.
- Кожне твердження про механізми, ефективність, поширеність має джерело, яке справді відкрито (WebFetch) і де це написано. Нічого з пам'яті. Не вигадувати посилання, DOI, цифри.
- Жодних цифр без джерела. Мова без перебільшень: «дослідження показують», «докази обмежені», не «доведено/гарантовано».
- Вказувати тип джерела й обмеження. Власні приклади й ілюстрації позначати як авторські.
- Мало джерел на вузьку тему: так і сказати в листі власнику, замість писати з припущень.
- Нічого про ліки, дози, діагностику, окрім скерування до лікаря.
- Перед надсиланням пройти `CONTENT-REVIEW-CHECKLIST.md` (розділи A–E) і коротко відзвітувати, що перевірено, а що викликає сумнів.

## Формат статті (`src/statti/<slug>.md`)
```
---
layout: article.njk
title: "Заголовок"
description: "До 160 символів"
category: "Категорія"
date: РРРР-ММ-ДД
reviewed: РРРР-ММ-ДД
updated: РРРР-ММ-ДД
seoTags: ["тег1", "тег2"]
section: statti
sectionLabel: "Матеріали"
sources:
  - title: "Автор, рік — Назва (журнал)"
    url: https://...
schema:
  "@context": "https://schema.org"
  "@type": "MedicalWebPage"
  "headline": "Той самий заголовок"
  "about":
    "@type": "MedicalCondition"
    "name": "Назва стану"
  "author":
    "@type": "Person"
    "name": "Сергій Коржов"
  "datePublished": "РРРР-ММ-ДД"
---
```
- **`sources` — лише об'єкти `title` + `url`**, не рядки (`npm test` попереджає про рядки). Усі джерела з тексту є в `sources` і навпаки; кожен URL відкривається.
- Перед створенням звірити поля з 1–2 найновішими статтями: сайт розвивається, зразок важливіший за цей шаблон.
- Категорії з власними іконками: `Тривожні розлади`, `Настрій`, `ОКР`, `Тіло і стрес`, `Сон` (інші назви теж працюють, з нейтральною іконкою; наявні також «Фобії», «Про терапію», «Травма і стрес», «Прокрастинація і саморегуляція»).
- `layout` для `/statti/` завжди `article.njk`. Значення з двокрапкою чи спецсимволами в лапках. Складний YAML писати в один рядок (без табуляцій).
- Структура: вступ (1–2 речення) → `## Що це таке` → механізм (з ілюстрацією) → `## Що допомагає` (3–5 КПТ-технік, точно названих) → `## Коли звертатись до фахівця` → за потреби посилання на квіз (`/kviz/tryvoga/`, `/kviz/depresiya/`, `/kviz/panichni-ataky/`, лише якщо тема справді відповідає) і на 1 наявну суміжну статтю. Внутрішні посилання тільки на наявні сторінки.
- Тема поза компетенцією (напр., ПТСР): поле `referOut: "текст"`.

## Формат поста блогу (`src/blog/<будь-яка-назва>.md`)
```
---
layout: blog-post.njk
title: "Заголовок"
description: "1–2 речення"
audience: colleagues   # або journal
date: РРРР-ММ-ДД
updated: РРРР-ММ-ДД
seoTags: [...]
sources:
  - title: "..."
    url: https://...
---
```
URL генерується з `title`. `layout` для `/blog/` завжди `blog-post.njk`. Чернетку, що не має публікуватись: `permalink: false` та `eleventyExcludeFromCollections: true`.

## Slug і зображення
- Slug статті: транслітерація латиницею, малі літери, дефіси, 2–4 змістові слова (не буквальний переклад заголовка й не англійська). Той самий slug для `src/statti/<slug>.md` і `src/assets/images/statti/<slug>/`.
- Кожна стаття має ≥1 концептуальну SVG-схему (не фото). Стиль: скруглені прямокутники/кола, стрілки, шрифт Inter. Палітра: `#3D5A4A` (акцент), `#C77A4F`, `#B5714A`, `#94897E`, фон `#EEF2EF`, картки `#FDFDFB`. Підписи не накладаються. Орієнтуватись на наявні SVG у `src/assets/images/statti/*/`.
- Вставка тільки HTML-тегом, шлях **абсолютний**:
  `<img src="/assets/images/statti/<slug>/<file>.svg" alt="Розгорнутий опис українською" width="W" height="H" style="max-width:100%;height:auto;">`
  `width`/`height` = `viewBox` SVG. Ніколи `![]()` і ніколи `../assets/...`.

## Чутливі теми
- Суїцид, самоушкодження, харчові розлади: без методів, цифр, дозувань; на початку абзац безпеки з **103/112** і посиланням на `/help/`.
- **Номер 0-800-500-335 не називати лінією «Ти як?»** (це «Ла Страда — Україна»). Телефони ліній брати лише зі сторінки `src/help.md`, не вигадувати й не писати з пам'яті.
- Політично чи соціально чутливі теми (напр., тривога через війну): лише психологічний механізм і доказові техніки, без політичних тверджень, без згадок конкретних подій (напр., «непереносимість невизначеності»).
- Не лякати: наявність симптому ≠ діагноз; статистика як групові середні; без «завжди/ніколи/небезпечно»; без звинувачень («візьміть себе в руки»). Не радити уникання, перевірки, пошук запевнень, придушення думок.

## Контент-план
Перед плануванням прочитати наявні `src/statti/` і `src/blog/` (title, category, seoTags), визначити прогалини за напрямками й не дублювати теми. План: тема, кут розкриття, цільовий запит, категорія, тип (стаття/пост), короткий список кандидатів у джерела. Показати власнику на затвердження, нічого не писати до затвердження.

## Перевірки
`npm install && npm test` перед кожним злиттям у `main`. `npm run build` для перевірки збірки. Помилка збірки в Actions: прочитати лог, виправити в гілці, не зливати зламане.
